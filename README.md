# НОКТЕНА · премиальный редизайн

Статическая витрина, каталог на JSON с динамическими переопределениями, защищённая `/admin/` и отдельный Railway proxy. Рабочий URL, API, авторизация и схема БД сохранены. Премиальная версия размещена из ветки `main` через GitHub Pages на `noktena.ru`; рабочая ветка изменений — `premium-redesign`.

## Структура

| Путь | Назначение |
| --- | --- |
| `index.html` | Главная, категории и каталог через существующие hash-маршруты |
| `product.html` | Карточка товара и выбор варианта |
| `checkout.html` | Корзина и оформление заказа |
| `assets/design-system.css` | Общие цвета, типографика, фокус и доступность |
| `assets/*-2026.css` | Стили витрины, товара и заказа поверх имеющихся компонентов |
| `assets/catalog-v2.js`, `assets/product-detail.js`, `assets/checkout.js`, `assets/cart.js` | Каталог, карточка и заказ |
| `admin/` | Актуальная защищённая админка; `admin-v2/` сохранена как старый маршрут |
| `admin/store-settings.js`, `assets/contact-settings.js` | Контакты магазина, подборка на главной и смена пароля |
| `data/` | Базовый каталог |
| `railway-admin/` | Прокси к Supabase Edge Functions; в этом редизайне не менялся |
| `supabase/functions/noktena-admin-api/` | Исходник защищённого метода смены пароля действующего API |
| `tests/analytics.test.cjs`, `tests/store-settings.test.cjs` | Проверки без реальных заказов и смены рабочего пароля |

Контент товара остаётся в JSON и серверных переопределениях. Дизайн-система не создаёт собственную базу. SEO-заголовок и описание карточки можно заполнить через редактор товара; значения хранятся в текущем payload товара.

## Локальный запуск

```bash
cd noktena
python3 -m http.server 8765
```

Откройте `http://localhost:8765/`, `http://localhost:8765/product.html?kind=mattress&model=...`, `http://localhost:8765/checkout.html` и `/admin/`. Сервер должен открывать сайт по HTTP: `fetch` локальных JSON не работает через `file://`. Каталог читает публичный bootstrap, а вход в админку требует действующей учётной записи. Локальный checkout по умолчанию обращается к рабочему API; **не отправляйте тестовый заказ без отдельного тестового backend**.

Сборщика у витрины нет. Проверка исходников:

```bash
for f in assets/*.js admin/*.js; do node --check "$f" || exit 1; done
node --test tests/analytics.test.cjs
# Для проверки серверной функции TypeScript требуется Node.js 24:
node --experimental-strip-types --test tests/store-settings.test.cjs
```

В `/admin/` откройте «Контакты», чтобы поменять телефон и ссылку MAX. Новые значения появятся на страницах после их обновления. «Популярные модели» задают до шести товаров в нужном порядке; до первого сохранения используется прежняя автоматическая подборка. «Пароль» требует текущий пароль; после смены потребуется войти заново. Пароль хранится и изменяется в Supabase Auth, а не в исходниках или каталоге.

Оформленные заказы сохраняются в админке. Письмо отправляет Railway proxy после сохранения заказа; `ORDER_EMAIL_TO` переопределяет адрес по умолчанию `noktena@mail.ru`. Наличие SMTP-переменных не подтверждает доставку: последняя проверенная попытка завершилась тайм-аутом соединения. Перед тем как полагаться на email-уведомления, необходимо наладить исходящую почту и проверить её без записи тестового заказа в рабочую базу.

Прокси запускается отдельно при необходимости: `cd railway-admin && npm ci && npm start` (Node.js 20+). Перед запуском сконфигурируйте переменные в окружении сервера; не добавляйте `.env` с секретами в Git.

## Переменные окружения прокси

| Переменная | Назначение |
| --- | --- |
| `PORT` | Порт HTTP, по умолчанию 3000 |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE` | Сервер уведомлений о заказах |
| `SMTP_USER`, `SMTP_PASS` | Учётные данные SMTP |
| `ORDER_EMAIL_TO`, `ORDER_EMAIL_FROM` | Адреса уведомлений |
| `MAX_BOT_TOKEN`, `MAX_CHAT_ID`, `MAX_USER_ID` | Необязательные уведомления через MAX |

Публичный адрес Supabase указан в proxy; приватные ключи и пароли в этом репозитории не требуются. Доступ администратора проходит через существующий серверный API и Supabase Auth. Счётчик Яндекс Метрики: `112921323`, файл `assets/yandex-metrika-config.js`.

## Безопасное размещение

1. Сверьте ветку `premium-redesign` с `main`; проверьте разметку, фильтры, карточки, корзину и админку с отдельным тестовым backend.
2. Проверьте payload заказа и уведомления на тестовой среде. Рабочие товары и заказы не использовать для экспериментов.
3. Проверьте Performance, Accessibility, Best Practices и SEO в Lighthouse, а также Chrome, Safari, Firefox и мобильные браузеры. Целевые оценки из ТЗ пока не подтверждены измерениями.
4. По разрешению владельца от 25.09.2026 ветка уже размещена через `main` и GitHub Pages на существующем домене. Старый `main` сохранён в `pre-premium-2026-09-25`; для следующих изменений повторите ревью в `premium-redesign`, затем объедините в `main`. Railway/Supabase и DNS не перенастраиваются. Workflow `test-cart-services.yml` выполняет только проверки без создания заказов. Одноразовые workflow, способные переписать страницы, переведены в ручной запуск.
5. Закрытая версия Sites только для просмотра содержит `preview-guard.js`: она читает каталог, блокирует запись в рабочий API и не отправляет события Метрики. Это отдельная копия, не исходник для выкладки на `noktena.ru`. Старый `main` сохраняется в истории Git для отката.

## Ограничения и протокол проверки

Аудит и план — в `AUDIT.md`, результаты и список изменений — в `REDESIGN_REPORT.md`. В доступном окружении не было тестовой базы и учётной записи админа. Реальное создание заказа, сохранение карточки и смена статуса заказа на рабочей базе намеренно не выполнялись. Текущая схема оформления не сохраняет способ оплаты: его согласовывает менеджер после получения заказа. Добавление полноценного способа оплаты требует отдельного согласованного изменения серверного контракта.
